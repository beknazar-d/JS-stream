# Разбор

Решение держится на двух переменных внутри батчера: `batch` (накопитель) и `scheduled` (отправка уже запланирована).

1. Первое уведомление серии добавляется в `batch` и планирует `flush` через `queueMicrotask`. Остальные уведомления того же прохода только добавляются: `scheduled` уже равно `true`.
2. Синхронный код заканчивается, event loop переходит к микрозадачам и вызывает `flush`. Это раньше любого таймера и без заметной задержки.
3. В `flush` порядок действий важен. Сначала `scheduled = false`, `batch` заменяется пустым массивом, и только потом вызывается `sendBatch(items)`. Если `sendBatch` сам вызовет `add`, новое уведомление попадёт в свежий `batch` и запланирует новую отправку. При обратном порядке (очистка после отправки) оно либо пропало бы, либо не запланировало бы отправку.
4. Пустая пачка невозможна: `flush` запланирован только после добавления хотя бы одного уведомления, и ровно один раз на серию.
5. Состояние лежит внутри `createNotificationBatcher`, поэтому два батчера независимы.

## Вопросы, которые стоило задать

- Что делать с ошибкой `sendBatch`: повторять, терять или пробрасывать?
- Нужно ли убирать одинаковые уведомления в пачке?
- Какие значения допустимы и нужен ли лимит размера пачки?
- Как важна задержка: допустима ли секунда ожидания ради большей пачки (тогда понадобился бы таймер)?

## Допущения в эталоне

Ошибки не глотаем и не повторяем, повторы не убираем, размер пачки не ограничиваем. Тесты эти решения не проверяют.
