# Разбор

Склад — это фабрика с тремя частями состояния в замыкании: `stock` (остатки), `reservations` (выданные резервы) и `nextId` (счётчик). Все четыре метода создаются в одном вызове, поэтому делят эти переменные. Снаружи их не видно.

Три решения, которые отличают рабочий модуль от ненадёжного.

1. **Копия на входе.** `const stock = { ...initialStock }`. Замыкание держит ссылки: если взять `initialStock` как есть, склад и вызывающий код будут работать с одним объектом. Резервы испортят чужие данные, а чужая правка испортит склад.
2. **Копия на выходе.** `snapshot()` отдаёт `{ ...stock }`, а не сам `stock`.
3. **Запись о резерве удаляется при снятии.** Тогда второй `release` не находит запись и возвращает `false`. Если запись оставить, один резерв можно «вернуть» много раз и получить остаток больше начального.

Проверка `Number.isInteger(qty) && qty >= 1` идёт раньше проверки артикула: некорректный запрос отклоняется независимо от склада.

## Вопросы, которые стоило задать

- Какое количество допустимо: только целое от 1? Бывают ли дробные единицы (метры, килограммы)?
- Объединять ли резервы одного артикула или каждый вызов отдельный?
- Как выглядит `id` и где его увидит человек?
- Нужна ли отдельная причина отказа для плохого количества?

## Допущения в эталоне

Допустимо только целое от 1, причина отказа для плохого количества `"bad-quantity"`, `id` вида `R-1`, резервы не объединяются. Тесты эти решения не проверяют.
