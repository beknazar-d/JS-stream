# Разбор

Функция — цикл с тремя исходами на каждом шаге. Главная мысль: каждый вид завершения запроса (ответ, неудача, отмена) обрабатывается отдельно и явно.

1. **Запрос только через `withTimeout`.** Он сам очищает таймер и отменяет запрос в полёте. Внешний `signal` передан третьим аргументом, поэтому отмена опроса мгновенно доходит до запроса и ответ, который придёт позже, нас уже не интересует.
2. **Отмена не равна неудаче.** В `catch` первым делом проверяем `signal?.aborted`: если опрос отменён, выбрасываем `signal.reason` и не считаем неудачу. Иначе отмена превратилась бы в «служба недоступна».
3. **Счётчик подряд.** `failures` обнуляется после каждого успешного ответа и растёт только на неудачах без перерыва. Третья неудача подряд даёт ошибку без лишней паузы.
4. **Колбэк по смене статуса.** Прошлый статус хранится в `lastStatus`. Колбэк вызывается только при смене, и вызывается до проверки на `delivered`, чтобы финальный статус тоже дошёл до интерфейса.
5. **Пауза через `sleep(intervalMs, signal)`.** Отмена прерывает её сразу, таймер очищается сам.

## Вопросы, которые стоило задать

1. Какие статусы, кроме `delivered`, финальные? Без ответа опрос `cancelled` посылки не остановится никогда.
2. Нужен ли общий предел времени опроса? Бесконечный опрос — это нагрузка на службу доставки.
3. Нужно ли увеличивать паузу после неудач? Этим займётся проект P4: там появится экспоненциальная пауза.
4. Что показывать клиенту при неудачах? Это решение интерфейса, но код должен дать ему повод: например, колбэк `onError`.
