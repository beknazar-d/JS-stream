# Разбор

Хорошо написанный этап 4 делает изменение дешёвым: формат ответа читается в одном месте, карточка строится в одном месте, запрос собирается в одном месте.

**Что менялось из-за API v2:**

1. `loadProducts`: вместо `data.items` и `data.total` читается `{ data, meta }`.
2. `formatPrice`: цена в копейках делится на 100 перед форматированием.
3. `createCard`: наличие считается по `stock > 0`, а не по булевому `inStock`.

**Что добавилось из-за новых требований:**

4. `category` и `sort` — части состояния. `buildQuery` добавляет их, только если они не значения по умолчанию.
5. Любая смена фильтра сбрасывает страницу на 1 по той же причине, что и поиск: при новых условиях старый номер страницы теряет смысл.

Совет на будущее: когда меняется формат данных, ищите весь код, который их читает. Если он разбросан по десяти местам, изменение дорого. Здесь это два места.

## Вопросы, которые стоило задать

- Что показывать, если у товара копейки (`priceMinor` не кратно 100)?
- Сбрасывать ли поиск при смене категории? Многие магазины сбрасывают, поведение «поиск внутри категории» бывает удобнее.
- Что с одинаковой ценой: стабильный порядок по популярности, по названию?
- Что показывать, если ни категория, ни поиск ничего не дали?
- Как долго будет жить версия 1? Нужна ли обратная совместимость?

## Допущения в эталоне

Копейки не показываются (в данных их нет), поиск сохраняется при смене категории, порядок одинаковых цен определяет сервер.
