## Зачем это в работе

Приходит письмо от владельца «Домотеки»: «Нужен каталог на сайте. Товары из нашего API, чтобы был поиск, фильтры, страницы. Чтобы не тормозило. Остальное решите сами».

Так выглядят настоящие заказы. Письмо короткое, в нём дыры, а через две недели прилетает «кстати, бэкенд поменял формат». Задача разработчика: уточнить, что неясно, собрать работающую версию по этапам, пережить изменения и сдать результат, которому можно доверять.

Это проект P3, мини-проект модуля 3. Он собирает всё, что вы выучили: DOM, события, `fetch`, состояния загрузки, дебаунс, отмену запросов и адрес страницы. Готовый проект можно положить в портфолио.

## Объяснение

Проект отличается от задания тем, что готовой формулировки нет. Есть пожелания, и из них нужно сделать правила. Порядок работы:

1. **Прочитать ТЗ и выписать вопросы.** В каждом задании проекта есть раздел «Неясности». До кода запишите в `assumptions.txt`, что неясно и какое допущение вы принимаете на время. Допущение должно легко меняться.
2. **Держать состояние в одном месте.** Поиск, категория, сортировка и страница лежат в одном объекте `state`. Запрос, поля и адрес выводятся из него. Если состояние размазано по переменным и по DOM, любое изменение требований оборачивается поиском по всему коду.
3. **Двигаться этапами.** Шесть этапов: первая страница, состояния, страницы, поиск, изменение требований, адрес страницы. Каждый следующий начинается с готового кода предыдущего.
4. **Встречать изменения спокойно.** На пятом этапе формат API меняется. Если чтение ответа и построение карточки собраны в двух функциях, перейти на новый формат дёшево.

Аналогия: ремонт кухни. Сначала замеры и чертёж (ТЗ и вопросы), потом черновая работа (данные и состояние), чистовая (поиск, фильтры), и приёмка после каждого этапа. Когда хозяйка просит поменять плиту, вы проверяете, что она не перерезала старую проводку.

## Пример

Главная идея проекта: страница — функция от состояния. Запрос собирается из `state`, значения по умолчанию в него не попадают.

<Playground example="query-from-state" />

То же с номерами страниц. Подпись и отключённые кнопки тоже выводятся, а не хранятся отдельно.

<Playground example="page-count" />

Так выглядит один шаг пользователя в коде. Сравните два подхода к смене категории.

<Wrong>

```js
categorySelect.addEventListener('change', () => {
  fetch('/api/products?category=' + categorySelect.value).then(render);
});
```

</Wrong>

<Right>

```js
categorySelect.addEventListener('change', () => {
  changeState({ category: categorySelect.value, page: 1 });
});
```

</Right>

Слева запрос теряет поиск, сортировку и страницу, не пишет адрес, не показывает загрузку и ошибку. Справа действие меняет состояние, а всё остальное выводится из него в одном месте.

## Как это работает

<Figure src="catalog-flow.svg" alt="Четыре блока по кругу. Вверху блок «Состояние»: q, category, sort, page. От него вниз влево идёт стрелка к блоку «Адрес», вниз вправо к блоку «Запрос к API». От запроса стрелка идёт к блоку «Экран» внизу. От экрана пунктир к адресу с подписью «Назад и Вперёд»." caption="Состояние в центре. Адрес, запрос и экран выводятся из него." />

Из схемы следует правило для каждого действия пользователя: изменить состояние, а дальше всё по цепочке. Из этого же следует, как устроены этапы.

**Этап 1. Данные на экране.** Запрос, JSON, карточки. Текст в карточки добавляется через `textContent`.

**Этап 2. Состояния.** У запроса четыре исхода: идёт, успех, пусто, ошибка. `fetch` не бросает исключение на ответ 503, поэтому `response.ok` проверяется вручную.

**Этап 3. Страницы.** Число страниц приходит от сервера. Границы проверяются и в отключённых кнопках, и в обработчиках: клик может прийти раньше, чем придёт ответ.

**Этап 4. Поиск.** Дебаунс стоит между полем и состоянием, а `AbortController` отменяет прошлый запрос. При новом поиске страница сбрасывается на 1.

**Этап 5. Изменение требований.** API меняет формат ответа (`data`, `meta`, цена в копейках), заказчик просит категории и сортировку. Смена фильтра сбрасывает страницу.

**Этап 6. Адрес страницы.** Состояние пишется в адрес через `pushState`. Кнопка «Назад» вызывает `popstate`: обработчик применяет состояние и не добавляет записей. Значения из адреса проверяются, потому что адрес может написать кто угодно.

<Note>

В учебной песочнице `location` не меняется при `pushState`. Поэтому состояние дополнительно кладётся в запись истории первым аргументом, а в тестах адрес читается через `currentUrl()`. В настоящем браузере `location.search` работает как обычно.

</Note>

## Типичные ошибки

Ошибки проекта почти не бросают исключений. Сообщения ниже получены в Chromium.

**1. Ответ 503 не считается ошибкой.** Если не проверить `response.ok`, код пойдёт читать поля, которых нет:

```text
TypeError: Cannot read properties of undefined (reading 'map')
```

<Wrong>

```js
const data = await response.json();
grid.replaceChildren(...data.items.map(createCard));
```

</Wrong>

<Right>

```js
if (!response.ok) throw new Error('HTTP ' + response.status);
const data = await response.json();
```

</Right>

**2. Отмена видна пользователю.** Без проверки имени ошибки каждая отменённая загрузка покажет «Не удалось загрузить каталог». Причина в консоли: `AbortError: signal is aborted without reason`. Проверьте `error.name === 'AbortError'` и выйдите молча.

**3. `pushState` внутри `popstate`.** Консоль чистая, но «Вперёд» перестаёт работать: новая запись обрезает историю после текущей.

<Wrong>

```js
window.addEventListener('popstate', (event) => {
  changeState(event.state); // changeState делает pushState
});
```

</Wrong>

<Right>

```js
window.addEventListener('popstate', (event) => {
  state = event.state ? { ...DEFAULT_STATE, ...event.state } : parseState(location.search);
  showControls();
  loadProducts();
});
```

</Right>

**4. Страница не сброшена.** Человек на третьей странице выбрал категорию из пяти товаров и видит пустой экран. Значение `page` нужно сбрасывать на 1.

**5. Копейки как рубли.** После перехода на API версии 2 чайник стоит `299 000 ₽`. Причина: забыли разделить `priceMinor` на 100. Ошибки нет, видно только глазами, поэтому тесты проверяют конкретные цены.

## Итог

Что вы теперь умеете:

- превращать короткое письмо заказчика в список вопросов и допущений;
- держать состояние в одном объекте и выводить из него запрос, поля и адрес;
- обрабатывать четыре исхода запроса и защищаться от устаревших ответов;
- переживать смену формата API и новые требования посередине проекта;
- хранить фильтры в адресе страницы и корректно работать с кнопками «Назад» и «Вперёд».

Модуль 3 закончен: вы умеете оживлять страницу в браузере. Дальше начинается модуль 4 «Асинхронность и глубокий JS» (готовится). Там вы узнаете, что на самом деле происходит с `await`, очередью задач и промисами, а код этого проекта получит надёжную основу под капотом.
