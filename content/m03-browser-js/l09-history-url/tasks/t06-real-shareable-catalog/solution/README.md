# Разбор

Идея решения: одно состояние (объект фильтров) и три пути к нему.

1. **Человек меняет элементы.** Обработчик `change` на форме читает значения, рисует список и делает `pushState`. Один обработчик на форму ловит все три контрола (событие всплывает).
2. **Человек нажимает «Назад» или «Вперёд».** Срабатывает `popstate`. Состояние берётся из `event.state`, которое мы записали сами. `null` означает самую первую запись: показываем значения по умолчанию. Здесь важно **не вызывать `pushState`**: переход по истории не должен создавать новых записей.
3. **Приходит готовый адрес.** `applyUrl(url)` разбирает его через `parseFilters` и показывает результат тем же `show`. В настоящем браузере при загрузке передают `location.pathname + location.search`. В тренажёре `location` не меняется, поэтому тесты вызывают `applyUrl` с нужной строкой.

`show(filters)` обновляет и элементы, и список. Это важно: после «Назад» значения в полях должны совпадать со списком, в том числе когда флажок надо снять.

Товары грузятся один раз. Пока `products` пуст, `render` рисует пустой список. После загрузки `render(current)` вызывается снова, поэтому адрес с фильтрами, обработанный до ответа API, не теряется. Сортировка идёт по копии `[...items]`, исходный массив не портится.

## Вопросы, которые стоило задать

1. Как упорядочивать товары с одинаковыми продажами? От этого зависит стабильность порядка в списке.
2. Что видит покупатель, пока товары грузятся, и если API не ответил? Нужен ли повтор запроса?
3. Нужно ли запоминать фильтры между визитами (`localStorage`) или достаточно адреса?
4. Что делать с несуществующей категорией в ссылке: показать всё или сообщение об ошибке? Решение молча берёт значение по умолчанию.
5. Должна ли смена сортировки создавать запись в истории или лучше заменять текущую (`replaceState`)? Для сортировки частый выбор: это не новая «страница».
