## Зачем это в работе

Тикет от поддержки: в карточке заказа написано `NaN кг`. Служба доставки вчера выкатила обновление и стала присылать вес строкой: `"2.5"` вместо `2.5`.

Откройте код. Там написано так:

```ts
const shipment = JSON.parse(text) as Shipment;
```

Компилятор доволен: `Shipment` говорит, что `weightKg` — число. Программа тоже выглядит правильно. Но TypeScript проверяет только то, что видит в коде. Содержимое ответа из сети он увидеть не может.

Этот урок про границу между сетью и вашей программой. На границе данные проверяют, и только после проверки они получают тип. Ошибки проверки возвращаются как значения, а не прячутся в исключениях.

## Объяснение

Откуда берутся данные, которых компилятор не видит? Из ответов API, файлов, полей формы, `localStorage` и `JSON.parse`. Типы TypeScript стираются при сборке: во время работы программы остаётся только JavaScript.

Представьте склад. Фургон привёз коробки с наклейками «Чайник, 2 кг». Наклейке можно верить, а можно вскрыть коробку и проверить. Тип `any` — это «верим всем наклейкам». Тип `unknown` — это закрытая коробка: пока не вскрыли и не проверили, ничего из неё достать нельзя.

Три инструмента этого урока:

- `unknown` (неизвестное значение) для всего, что пришло снаружи;
- охранник типа (type guard) — функция, которая проверяет значение и сообщает компилятору результат. После неё тип в ветке сужается;
- `Result` — тип, в котором успех и ошибка лежат рядом и различаются полем `ok`.

Зачем нужен `Result`, если есть исключения? Исключение не видно в сигнатуре функции. Глядя на `getShipment(id): Shipment`, не узнаешь, что она может упасть. А `Promise<Result<Shipment, ApiError>>` честно говорит: бывает успех, бывает ошибка, и компилятор заставит проверить, что именно пришло.

## Как это работает

<Figure src="api-boundary.svg" alt="Схема слева направо. Блок «Сеть» с типом unknown передаёт данные блоку «Проверка» (охранник или разбор). Из проверки выходят две стрелки: верхняя ведёт к блоку Shipment с пометкой ok: true, нижняя к блоку ApiError с пометкой ok: false." caption="Проверка стоит на границе. Дальше по программе идут только надёжные данные или ошибка." />

Как компилятор сужает `unknown` до объекта с полями. Проверки идут цепочкой, и каждая даёт компилятору новую информацию:

1. `typeof value === 'object'` оставляет `object | null`.
2. `value !== null` убирает `null`.
3. `'id' in value` говорит, что свойство `id` есть. Его тип пока `unknown`.
4. `typeof value.id === 'number'` сужает его до числа.

Каждая проверка нужна. Пропустите вторую, и `'id' in value` упадёт на `null`.

**Охранник типа.** Запись `value is Courier` в возвращаемом типе — предикат (predicate). Это обещание: «если я вернул `true`, значение — `Courier`». Компилятор не проверяет, что вы выполнили обещание, поэтому охранник пишут особенно внимательно. Ошибка в нём хуже ошибки в `as`: она спрятана в функции, которой все доверяют.

**Result.** Тип `Result<T, E>` — размеченное объединение (discriminated union): поле `ok` различает ветки. В ветке `ok: true` есть `value`, в ветке `ok: false` есть `error`. Пока вы не проверили `ok`, читать `value` нельзя: компилятор не знает, какая ветка перед ним.

**Ошибка в типе, а не в исключении.** Когда запрос может сломаться тремя способами, ошибку тоже делают размеченным объединением по полю `kind`. Тогда `switch` по `kind` проверяется на полноту: забытый вид ошибки заметит компилятор.

```ts
type ApiError =
  | { kind: 'network'; message: string }
  | { kind: 'http'; status: number }
  | { kind: 'invalid'; problems: string[] };
```

<Note>

Валидатор по возможности собирает все проблемы, а не останавливается на первой. Тот, кто чинит данные, увидит всё сразу. Для единственного значения, как `parseWeight`, хватает одной строки ошибки. Для объекта с полями удобен массив.

</Note>

Откуда брать `fetch`? Функция, которая ходит в сеть, получает его параметром: `fetchLike`. Тогда в тестах вместо сети стоит заглушка, а в браузере настоящий `fetch`. Это тот же приём, что передача текущей даты параметром.

## Типичные ошибки

Все сообщения компилятора ниже получены запуском `tsc` 6.0.3 в режиме `strict`. Сообщения среды выполнения получены запуском в Node.js 22.

**1. Читают поле у `unknown`.**

<Wrong>

```ts
const data: unknown = JSON.parse('{"id":"S-1"}');
console.log(data.id);
```

</Wrong>

```text
error TS18046: 'data' is of type 'unknown'.
```

Компилятор не даёт читать поля у неизвестного значения. Сузьте тип: проверьте объект, затем поле. Не лечите ошибку заменой на `any`.

**2. Неизвестное значение передают туда, где нужен конкретный тип.**

<Wrong>

```ts
declare function label(name: string): string;
const raw: unknown = JSON.parse('{}');
label(raw);
```

</Wrong>

```text
error TS2345: Argument of type 'unknown' is not assignable to parameter of type 'string'.
```

То же самое, только в вызове функции. Решение: `typeof raw === 'string'` перед вызовом.

**3. Читают `value` у `Result` без проверки `ok`.**

<Wrong>

```ts
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
declare const result: Result<number, string>;
console.log(result.value);
```

</Wrong>

```text
error TS2339: Property 'value' does not exist on type 'Result<number, string>'.
  Property 'value' does not exist on type '{ ok: false; error: string; }'.
```

Вторая строка объясняет причину: у ветки с ошибкой поля `value` нет. Напишите `if (result.ok)`, и внутри всё заработает.

<Right>

```ts
if (result.ok) {
  console.log(result.value);
}
```

</Right>

**4. После `as` данные оказались другими.** Компилятор молчит, а программа падает позже и далеко от места ошибки.

<Wrong>

```ts
const shipment = JSON.parse('{"courier":null}') as { courier: { name: string } };
console.log(shipment.courier.name);
```

</Wrong>

```text
TypeError: Cannot read properties of null (reading 'name')
```

Приведение `as` ничего не проверило. Исправление такое же, как в примере выше: `unknown`, охранник, проверка.

**5. Охранник вернул `boolean`.** Функция проверяет всё правильно, но в сигнатуре нет `value is …`. Тогда сужения не происходит, и дальше в коде появляется `as`. Ошибка не в сообщении, а в привычке: когда пишете `as` сразу после проверки, посмотрите на тип возврата охранника.
