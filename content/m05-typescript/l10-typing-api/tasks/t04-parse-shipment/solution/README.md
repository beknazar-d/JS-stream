# Разбор

Функция состоит из трёх слоёв.

1. **Охранники для частей.** `isRecord` отсекает `null`, массивы и примитивы, а `isShipmentStatus` и `isPositiveNumber` проверяют отдельные поля. Каждый возвращает предикат (`value is …`), поэтому после проверки переменная получает точный тип.
2. **Сбор проблем.** Проверки не выходят из функции, а добавляют строку в `problems`. Разработчик, который чинит данные, видит все проблемы сразу.
3. **Сборка значения.** Результат строится из проверенных переменных, а не из `raw`. Поэтому лишние поля не попадают в `value`, а типы совпадают с `Shipment` без единого `as`.

Почему в последнем условии проверки повторяются? Компилятор не умеет понять, что пустой `problems` означает «все поля верные». Он сужает типы только из прямых проверок в условии. Повтор стоит дёшево и честнее приведения типа: если кто-то изменит правило в одном месте и забудет другое, компилятор укажет на несоответствие.

Для вложенного объекта вспомогательная функция `readCourier` возвращает три исхода одним значением: `Courier`, `null` или `undefined` для «неверно». Так различаются «курьера нет» и «курьер сломан».

Тип `Result` заставляет вызывающий код проверить `ok`: пока проверки нет, `result.value` не компилируется.
