# Разбор

Функция проходит три границы, и у каждой свой вид ошибки.

1. **Сеть.** `fetchLike` может отклонить промис: нет связи, таймаут. Это `kind: 'network'`. Вызов обёрнут в `try/catch`, а текст ошибки берётся безопасно: в `catch` значение имеет тип `unknown`, поэтому нужна проверка `error instanceof Error`.
2. **Статус.** Ответ 404 или 503 не является отклонением промиса, он приходит как обычный ответ с `ok: false`. Это `kind: 'http'`. Тело не читаем: оно может быть HTML-страницей ошибки.
3. **Тело.** `json()` тоже может отклониться, если пришёл не JSON. Результат — `unknown`, и его проверяет `parseShipment`. Её список проблем превращается в `kind: 'invalid'`.

Тип `Promise<Result<Shipment, ApiError>>` — договор: вызывающий код видит ошибки в типе, а не ловит исключения. Поэтому функция никогда не отклоняется: все пути ведут к `return`.

Последняя строка возвращает `parsed`, когда он успешен. Компилятор принимает это: после проверки `!parsed.ok` оставшаяся ветка имеет тип `{ ok: true; value: Shipment }`, который входит в `Result<Shipment, ApiError>`.

## Вопросы, которые стоило задать

- Что делать с ответом 204 или 200 без тела?
- Повторять ли запрос при 503 и сетевых ошибках, и сколько раз?
- Нужна ли проверка идентификатора до запроса?
- Нужен ли заголовок авторизации и откуда брать токен?

## Допущения в эталоне

Пустое тело считается неверным JSON, повторов нет, идентификатор не проверяется, но кодируется. Тесты эти решения не проверяют.
