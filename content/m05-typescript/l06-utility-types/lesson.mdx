## Зачем это в работе

В «Домотеке» у заказа шесть полей. Из этого одного описания нужны сразу четыре вида:

- превью для списка в личном кабинете: только номер и статус;
- форма создания: все поля, кроме номера и даты, которые ставит сервер;
- патч для редактирования: любые поля по отдельности, но не номер;
- справочник подписей: для каждого статуса своя русская надпись.

Новичок копирует поля в четыре новых интерфейса. Через месяц в `Order` появляется поле `courierId`, а в трёх копиях его нет. Ошибка не видна, пока заказ не придёт в неправильном виде.

Нужен способ сказать «возьми `Order` и измени вот так». В TypeScript для этого есть набор готовых преобразований типов — utility types.

## Объяснение

Представьте типографию. Макет один — заказ. Из него печатают визитку (только имя и телефон), бланк для заполнения (пустые поля) и копию под стеклом (менять нельзя). Макет правят в одном месте, а все виды обновляются сами.

Utility types — это такие «печатные станки». Каждый получает тип и возвращает новый тип. Запись `Partial<Order>` читается как «Partial от Order». В угловых скобках лежит исходный тип, как у обобщений из прошлого урока. Utility types и есть обобщённые типы, которые уже написаны за вас.

Восемь самых нужных:

- `Partial<T>` — все поля необязательные.
- `Required<T>` — все поля обязательные.
- `Readonly<T>` — поля нельзя менять после создания.
- `Pick<T, Keys>` — оставить только перечисленные поля.
- `Omit<T, Keys>` — убрать перечисленные поля.
- `Record<Keys, Value>` — объект, у которого ровно эти ключи и значения одного типа.
- `ReturnType<F>` — тип результата функции.
- `Parameters<F>` — типы параметров функции в виде кортежа (tuple, массива фиксированной длины).

Перечень `Keys` пишут строковыми типами через вертикальную черту: `"id" | "status"`.

## Как это работает

Каждый из «станков» устроен просто: он берёт поля исходного типа и выпускает такие же с поправкой. Посмотрите на схему.

<Figure src="utility-map.svg" alt="Слева прямоугольник с типом Order и полями id, status, city, total. Справа четыре прямоугольника со стрелками от Order: Pick оставляет только id и status; Omit убирает id; Partial делает все поля необязательными; Readonly запрещает менять поля." caption="Один исходный тип, четыре производных. Добавили поле в Order, и оно появилось во всех видах автоматически." />

Правила, которые стоит запомнить.

1. Utility types существуют только во время проверки типов. В JavaScript от них ничего не остаётся. `Readonly<Order>` не заморозит объект: он только запретит компилятору присваивать.
2. `Pick` и `Omit` принимают только настоящие названия полей. Опечатка `"idd"` в `Pick` даёт ошибку, а в `Omit` нет: он принимает любые строки. Поэтому `Omit<Order, "idd">` молча ничего не уберёт. Будьте внимательны.
3. `Partial` — только верхний уровень. Если внутри заказа вложенный адрес, его поля останутся обязательными.
4. `ReturnType` и `Parameters` принимают тип функции, а не саму функцию. Чтобы получить тип из значения, пишут `typeof calcFee`. Слово `typeof` в типах означает «тип вот этого значения».
5. Преобразования можно вкладывать друг в друга: `Readonly<Pick<Courier, "name" | "zone">>`.

<Note>

`Record<string, number>` — это «любой набор строковых ключей с числовыми значениями». А `Record<DeliveryStatus, number>` — «ровно четыре ключа». Первый ничего не требует, второй требует все ключи. Для справочников используйте второй.

</Note>

## Типичные ошибки

Сообщения получены запуском компилятора TypeScript 6.0.3 в режиме `strict`.

**1. Опечатка в названии поля у `Pick`.**

<Wrong>

```ts
type Preview = Pick<Order, "idd">;
```

</Wrong>

```text
error TS2344: Type '"idd"' does not satisfy the constraint 'keyof Order'.
```

Компилятор говорит: такого ключа у `Order` нет. Проверьте написание.

**2. В `Record` пропустили ключи.**

<Wrong>

```ts
const labels: Record<Status, string> = { new: "Новый" };
```

</Wrong>

```text
error TS2739: Type '{ new: string; }' is missing the following properties from type 'Record<Status, string>': paid, shipped
```

Сообщение перечисляет недостающие ключи. Добавьте их все.

**3. Меняем поле у `Readonly`.**

<Wrong>

```ts
const order: Readonly<Order> = { id: 1, status: "new", city: "Омск", total: 5 };
order.status = "paid";
```

</Wrong>

```text
error TS2540: Cannot assign to 'status' because it is a read-only property.
```

Если менять нужно, создайте новый объект: `{ ...order, status: "paid" }`.

**4. Читаем поле у `Partial` без проверки.**

<Wrong>

```ts
const draft: Partial<Order> = {};
draft.city.toUpperCase();
```

</Wrong>

```text
error TS18048: 'draft.city' is possibly 'undefined'.
```

У `Partial` любое поле может отсутствовать. Проверьте его перед использованием: `draft.city?.toUpperCase()`.

**5. Передали функцию там, где нужен её тип.**

<Wrong>

```ts
type Fee = ReturnType<calcFee>;
```

</Wrong>

```text
error TS2749: 'calcFee' refers to a value, but is being used as a type here. Did you mean 'typeof calcFee'?
```

<Right>

```ts
type Fee = ReturnType<typeof calcFee>;
```

</Right>

## Итог

Что вы теперь умеете:

- получать из одного типа несколько видов через `Partial`, `Required`, `Readonly`, `Pick` и `Omit`;
- описывать справочники, где обязаны быть все ключи, через `Record`;
- брать типы у готовой функции через `ReturnType` и `Parameters` вместе с `typeof`;
- помнить, что utility types не создают защиты во время выполнения.

В следующем уроке мы соберём все эти идеи в разбор ловушек: `any`, приведение `as`, восклицательный знак `!`. Это то, что чаще всего ломает типы в настоящем коде.
