# Разбор

Все типы выводятся из `DeliverySettings`, поэтому поле, добавленное в интерфейс, появится везде само.

- `SettingsOverride = Partial<DeliverySettings>` — регион указывает только нужные поля, пустой объект тоже допустим.
- `ResolvedSettings = Readonly<Required<DeliverySettings>>` — преобразования вкладываются. `Required` делает необязательную `note` обязательной, `Readonly` запрещает менять поля. Читать запись нужно изнутри наружу.
- `PublicSettings = Pick<ResolvedSettings, ...>` — три поля, и `readonly` сохраняется, потому что `Pick` берёт модификаторы исходного типа.
- `CalcFeeArgs = Parameters<typeof calcFee>` и `Fee = ReturnType<typeof calcFee>` — типы берутся из функции. Если изменить сигнатуру `calcFee`, они обновятся сами. Слово `typeof` нужно, потому что `calcFee` — значение, а не тип.

`resolveSettings` строит новый объект и для каждого поля берёт `override.x ?? defaults.x`. Так `undefined` пропускается, а общие настройки остаются нетронутыми. Запись `{ ...defaults, ...override }` здесь неверна: спред копирует и `undefined`.

`publicSettings` собирает объект из трёх полей вручную. `Pick` — это тип, а не операция: он не убирает лишние поля из значения во время выполнения. Если вернуть весь объект `settings`, заметка `note` уйдёт наружу.

## Вопросы, которые стоило задать

- Допустимы ли отрицательные и нулевые значения? Кто их проверяет?
- Округлять ли стоимость и как?
- Какие поля считаются внутренними, а какие публичными?
- Нужно ли проверять, что валюты региона и заказа совпадают?

## Допущения в эталоне

Значения принимаются как есть, без округления и проверок. Публичные поля: `baseFee`, `perKg`, `currency`. Тесты этих решений не проверяют.
