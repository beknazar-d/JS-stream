## Зачем это в работе

В «Домотеке» нужна функция «взять первый элемент списка»: первый заказ в очереди, первый курьер на смене, первая посылка на складе.

Первая версия выглядит так.

```ts
function firstItem(items: any[]): any {
  return items[0];
}
```

Она работает с чем угодно. Но тип `any` выключает проверку. Вы получили заказ, а компилятор думает, что это что угодно. Опечатка в `firstItem(orders).cty` пройдёт молча, а упадёт уже у покупателя.

Можно написать три функции: для заказов, для курьеров, для посылок. Но тело у них одинаковое, и править придётся три раза.

Нужна одна функция, которая запоминает, какой тип ей дали, и возвращает именно его. Это и есть обобщения (generics).

## Объяснение

Представьте бланк накладной с пустой графой «Что везём». Бланк один. Когда на складе его заполняют, в графу вписывают «Заказ» или «Курьер». Остальной текст бланка не меняется.

Параметр типа (type parameter) — такая графа. Его пишут в угловых скобках после имени функции: `function firstItem<T>(...)`. Имя `T` — просто привычка (от Type). Можно писать `Item` или `TOrder`, но однобуквенные имена в коротких функциях удобнее.

Читать запись `firstItem<T>(items: T[]): T | undefined` нужно так: «Для любого типа T: функция берёт массив значений T и возвращает T или `undefined`».

Тип `T` обычно не пишут руками. Компилятор выводит его из аргумента (type argument inference): передали `Order[]`, значит `T` равно `Order`.

Обобщёнными бывают не только функции, но и типы. `interface Page<T>` описывает страницу списка с любыми элементами: `Page<Order>`, `Page<Courier>`.

Два уточнения, которые пригодятся в работе:

- Ограничение (constraint). Запись `T extends { id: number }` говорит: «T — любой тип, у которого есть числовое поле `id`». Внутри функции можно читать `item.id`, а снаружи нельзя передать значение без `id`.
- Значение по умолчанию (default). Запись `interface Page<T = string>` говорит: «если T не указан, это `string`».

## Как это работает

Параметр типа живёт только при проверке. Компилятор смотрит на вызов, находит `T`, подставляет и проверяет код. В готовом JavaScript никаких `T` нет: все типы стираются.

<Figure src="generic-slots.svg" alt="Схема: в центре функция firstItem с параметром T. Слева стрелка от вызова firstItem(orders): T равно Order, результат Order или undefined. Справа стрелка от вызова firstItem(couriers): T равно string, результат string или undefined." caption="Одна функция, два вызова: компилятор подставляет свой T в каждом месте вызова отдельно." />

Три правила, которые стоит запомнить.

1. Тип выводится из аргументов. Если выведенный тип не подходит, можно указать его вручную: `firstItem<Order>(items)`. Это нужно, когда аргументов нет, например `toPage<Order>([])`. Но в остальных случаях хватает вывода.
2. Если параметров типа несколько, указывать нужно все или никакие. Вариант `pair<string>('a', 1)` для функции с `<A, B>` — ошибка. Исключение: у параметров есть значения по умолчанию.
3. Без ограничения о `T` известно только то, что это «какой-то тип». Читать у него поля нельзя. Ограничение `extends` даёт право на конкретные поля, но вызывающий всё равно получает свой, более точный тип.

Про слово `extends` здесь. В `T extends { id: number }` оно значит «подходит под описание», а не наследование класса. Любой тип, где есть `id: number`, подходит. Лишние поля допустимы.

Ещё одна мысль. Обобщения нужны, когда тип результата зависит от типа входа. Если функция всегда возвращает `number`, параметр типа не нужен. Правило: если `T` встречается в сигнатуре только один раз, он, скорее всего, лишний.

<Note>

Параметр типа «запоминает» тип. Объединение (union) `Order | Courier` его не запоминает. Функция `(items: (Order | Courier)[]) => Order | Courier` вернёт «или то, или другое», и придётся сужать вручную. С `T` результат сразу точный.

</Note>

## Типичные ошибки

Сообщения получены запуском компилятора TypeScript 6.0.3 в режиме `strict`.

**1. Читаем поле у типа без ограничения.**

<Wrong>

```ts
function idOf<T>(item: T) {
  return item.id;
}
```

</Wrong>

```text
error TS2339: Property 'id' does not exist on type 'T'.
```

Про `T` известно только то, что он существует. Скажите компилятору больше: `T extends { id: number }`.

<Right>

```ts
function idOf<T extends { id: number }>(item: T) {
  return item.id;
}
```

</Right>

**2. Забыли параметр у обобщённого типа.**

<Wrong>

```ts
interface Page<T> {
  items: T[];
}
const page: Page = { items: [] };
```

</Wrong>

```text
error TS2314: Generic type 'Page<T>' requires 1 type argument(s).
```

`Page` без аргумента не тип, а заготовка. Напишите `Page<Order>` или задайте значение по умолчанию: `Page<T = string>`.

**3. Передали не то, что подходит под ограничение.**

<Wrong>

```ts
const couriers = [{ name: "Анна" }];
findById(couriers, 1);
```

</Wrong>

```text
error TS2345: Argument of type '{ name: string; }[]' is not assignable to parameter of type '{ id: number; }[]'.
  Property 'id' is missing in type '{ name: string; }' but required in type '{ id: number; }'.
```

Вторая строка сообщения объясняет причину: нет поля `id`. Читайте обе строки.

**4. Указали тип вручную неверно.**

<Wrong>

```ts
const first = firstItem<number>(["Анна"]);
```

</Wrong>

```text
error TS2322: Type 'string' is not assignable to type 'number'.
```

Вручную указанный `T` выигрывает у вывода, и аргумент проверяется по нему. Обычно лучше убрать `<number>` и дать компилятору вывести тип самому.

**5. Забыли, что результат может быть пустым.**

<Wrong>

```ts
const first = firstItem([1, 2]);
first.toFixed(1);
```

</Wrong>

```text
error TS18048: 'first' is possibly 'undefined'.
```

Функция честно вернула `T | undefined`. Проверьте значение перед использованием: `first?.toFixed(1)` или `if (first !== undefined)`.

## Итог

Что вы теперь умеете:

- писать функцию и тип с параметром типа `T` и объяснять, откуда компилятор берёт его значение;
- ограничивать параметр через `extends`, чтобы читать у него поля;
- задавать значение по умолчанию и понимать, когда тип нужно указать вручную;
- видеть, когда `any` можно заменить параметром типа.

Теперь вы можете описывать собственные «шаблоны» типов. Но частые шаблоны уже написаны за вас: `Partial`, `Pick`, `Record`. В следующем уроке разберём их и соберём из них типы для заказов, не копируя поля вручную.
