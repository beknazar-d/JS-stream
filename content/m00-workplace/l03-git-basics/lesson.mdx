## Зачем это в работе

Вы переписали функцию расчёта доставки. Через два часа выяснилось, что старая версия работала лучше. Вернуть её нечем: вы сохранили файл поверх. Хуже того, вчерашний коллега поправил тот же файл, и теперь непонятно, чьи изменения где.

Именно для этого придумали систему контроля версий (version control system). Самая распространённая из них — Git. Она хранит историю всех изменений проекта: кто, когда и что поменял. Любую версию можно вернуть. Любой чужой кусок кода можно получить.

Без Git сегодня не работает почти ни одна команда. Резюме без ссылки на GitHub выглядит странно. В этом уроке вы создадите первый репозиторий, сделаете коммит и отправите проект на GitHub.

## Объяснение

Репозиторий (repository, сокращённо «репо») — папка проекта вместе с её историей. Git прячет историю в скрытой подпапке `.git`. Удалите её, и папка снова станет обычной.

Коммит (commit) — один снимок проекта с подписью. В подписи вы коротко пишете, что изменили.

Представьте отправку посылки. Вы раскладываете вещи по столу (рабочая папка). Откладываете в коробку то, что хотите отправить (команда `git add`). Заклеиваете коробку и пишете на ней, что внутри (команда `git commit`). Отправляете на склад (команда `git push`). Коробка запечатана навсегда: её содержимое уже не изменить, только отправить следующую.

Три места, через которые проходит каждое изменение:

- рабочая папка: ваши файлы, которые вы правите;
- индекс (index, также staging area, «область подготовки»): коробка, в которую вы отложили изменения для следующего коммита;
- история: коммиты, уже записанные в репозиторий.

### Установка и первая настройка

1. Установите Git с сайта `git-scm.com`. На Windows вместе с ним ставится Git Bash — терминал, где работают команды из прошлого урока в стиле macOS и Linux.
2. Откройте новый терминал и проверьте: команда `git --version` печатает версию, например `git version 2.43.0`.
3. Один раз скажите Git, кто вы. Имя и почта будут записаны в каждый ваш коммит.

```text
$ git config --global user.name "Anna Ivanova"
$ git config --global user.email "anna@example.com"
```

Слово `--global` значит «для всех моих репозиториев на этом компьютере». Если не сделать настройку, первый же коммит остановится. Вы увидите это в разделе ошибок.

## Пример

Создадим репозиторий. Выполняйте шаги на своём компьютере. Чек-лист в разделе «Задания» повторяет их по порядку.

```text
$ mkdir shop
$ cd shop
$ git init -b main
Initialized empty Git repository in /home/anna/demo/shop/.git/
```

`git init` (initialize) создаёт репозиторий. Параметр `-b main` называет основную ветку `main`. Ветка (branch) — это линия истории; пока она у нас одна.

Добавьте в папку два файла: `README.md` и `hello.js`. Теперь главная команда `git status`: она всегда говорит, что происходит.

```text
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	hello.js

nothing added to commit but untracked files present (use "git add" to track)
```

Слово «Untracked» значит, что Git пока не следит за этими файлами. Отложим в коробку один из них и посмотрим ещё раз.

```text
$ git add README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	hello.js
```

Файл `README.md` теперь в разделе «Changes to be committed»: он в коробке. А `hello.js` по-прежнему вне. Заклеим коробку.

```text
$ git commit -m "Добавить README"
[main (root-commit) 6624f2c] Добавить README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

Параметр `-m` (message) задаёт подпись. Без него Git откроет текстовый редактор, и новички часто не понимают, как из него выйти. Хеш `6624f2c` у вас будет другим: это уникальный номер коммита.

Добавим второй файл и посмотрим историю.

```text
$ git add .
$ git commit -m "Добавить скрипт hello.js"
$ git log --oneline
f98d476 Добавить скрипт hello.js
6624f2c Добавить README
```

Точка в `git add .` значит «текущая папка целиком» (вы знаете эту точку из прошлого урока). `git log` печатает историю от нового к старому, а `--oneline` сокращает каждый коммит до одной строки.

Хорошая подпись коммита отвечает на вопрос «что делает этот коммит». Пишите коротко и в одном стиле: «Добавить расчёт доставки», «Исправить округление скидки».

## Как это работает

Откуда Git знает, что в какой коробке? Для этого и есть компактная форма `git status --short`. Каждая строка состоит из двух символов кода, пробела и имени файла.

<Playground example="status-line" />

Первый символ описывает индекс, второй — рабочую папку:

- `M` изменён (modified), `A` добавлен (added), `D` удалён (deleted), `R` переименован (renamed);
- пробел — «в этом месте изменений нет»;
- `??` — файл новый, Git за ним ещё не следит.

Вот реальный вывод проекта, где все случаи сразу.

```text
 D README.md
D  docs/guide.md
 M "price lists/may 2026.csv"
M  src/cart.js
 M src/order.js
R  src/legacy.js -> src/orders-v2.js
MM src/stock.js
A  src/utils.js
?? notes.txt
?? reports/
```

Прочитайте построчно:

- `M  src/cart.js` — изменение уже в коробке, войдёт в коммит;
- ` M src/order.js` — изменено, но в коробку ещё не положено;
- `MM src/stock.js` — часть изменений в коробке, а после этого файл правили ещё раз. В коммит попадёт только версия из коробки;
- `R  src/legacy.js -> src/orders-v2.js` — файл переименован, показаны старое и новое имя;
- имя с пробелом Git берёт в кавычки.

### Что не нужно коммитить

В папке проекта есть файлы, которые не должны попадать в историю: пароли и ключи (`.env`), скачанные библиотеки (`node_modules`), логи. Их перечисляют в файле `.gitignore`: по одному правилу в строке.

```text
node_modules/
.env
*.log
```

После создания `.gitignore` Git перестаёт предлагать эти файлы. Сам `.gitignore` коммитят, как обычный файл.

```text
$ git status --short
?? .env
?? node_modules/
$ printf 'node_modules/\n.env\n' > .gitignore
$ git status --short
?? .gitignore
```

Правила читаются так:

- `*.log` — любые файлы с расширением `.log` в любой папке;
- `node_modules/` — папка с таким именем и всё внутри;
- `.env` — файл с этим именем.

<Playground example="gitignore-rules" />

<Note>

Если секретный файл уже попал в коммит, `.gitignore` не поможет: история его помнит. Пароль считается утёкшим, его нужно заменить. Поэтому создавайте `.gitignore` до первого `git add .`.

</Note>

### Отправка на GitHub

GitHub — сайт, который хранит копии репозиториев. Он бесплатный. Зачем он нужен:

- резервная копия: сломали компьютер — проект на месте;
- работа в команде: коллеги получают ваш код;
- портфолио: работодатель видит ваши проекты.

Порядок такой.

1. Зарегистрируйтесь на `github.com` и нажмите «New repository». Назовите его `shop`. Галочки «Add a README» не ставьте: у вас уже есть свой.
2. GitHub покажет адрес репозитория, например `https://github.com/anna/shop.git`. Свяжите с ним вашу папку.
3. Отправьте историю.

```text
$ git remote add origin https://github.com/anna/shop.git
$ git push -u origin main
```

`git remote add origin адрес` запоминает адрес под коротким именем `origin` (удалённый репозиторий, remote). `git push -u origin main` отправляет ветку `main`. Ключ `-u` запомнит связь, и дальше хватит команды `git push`.

GitHub не принимает пароль от аккаунта при отправке. Войти можно через браузер: Git для Windows ставится с программой Git Credential Manager, которая сама откроет окно входа. Другой путь — GitHub CLI: команда `gh auth login`. Актуальные способы описаны в документации GitHub, раздел про аутентификацию при работе с Git. Если застряли, не отчаивайтесь: это единственное сложное место урока, его проходят все.

## Типичные ошибки

Все сообщения получены запуском Git 2.43 в терминале.

**1. Git не знает, кто вы.**

```text
$ git commit -m "Добавить README"
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.
```

Git просит вписать имя и почту. Выполните две команды из подсказки со своими данными и повторите коммит.

**2. Коммитить нечего.**

```text
$ git commit -m "ещё раз"
On branch main
nothing to commit, working tree clean
```

Все изменения уже в истории. Либо вы ничего не меняли, либо забыли сохранить файл в редакторе.

**3. Опечатка в имени файла.**

<Wrong>

```text
$ git add helo.js
fatal: pathspec 'helo.js' did not match any files
```

</Wrong>

`pathspec` — «путь к файлу». Git не нашёл такого. Проверьте имя через `ls`.

**4. Забыли `-m`.**

<Wrong>

```text
$ git commit "Добавить README"
error: pathspec 'Добавить README' did not match any file(s) known to git
```

</Wrong>

Без `-m` Git считает текст именем файла. Правильно: `git commit -m "Добавить README"`.

**5. Отправка без адреса.**

```text
$ git push
fatal: No configured push destination.
Either specify the URL from the command-line or configure a remote repository using

    git remote add <name> <url>

and then push using the remote name

    git push <name>
```

Git не знает, куда отправлять. Сначала выполните `git remote add origin адрес`. Сообщение само подсказывает нужную команду.

## Итог

Что вы теперь умеете:

- создать репозиторий командой `git init` и сделать первый коммит через `git add` и `git commit -m`;
- читать `git status` и `git status --short`: что в индексе, что изменено, что новое;
- смотреть историю командой `git log --oneline`;
- не коммитить лишнее: `node_modules`, `.env`, логи — через `.gitignore`;
- опубликовать проект на GitHub командами `git remote add` и `git push`.

Теперь вы можете запускать код, ходить по папкам и сохранять историю. Остаётся научиться читать сообщения об ошибках и пользоваться инструментами отладки. Следующий урок — про ошибки и DevTools, и после него вы готовы к модулю 1.
