## Контекст

Тикет PUBLISH-12. В скрипте публикации нужен отчёт «что произойдёт при коммите», чтобы ничего лишнего не ушло в историю. Для отчёта скрипт запускает `git status --short` и получает текст. Его надо разобрать на три списка: что войдёт в коммит, что изменено, но не добавлено, и что новое и не отслеживается.

Реальный вывод `git status --short` на проекте, где собраны все основные случаи:

```text
$ git status --short
 D README.md
D  docs/guide.md
 M "price lists/may 2026.csv"
M  src/cart.js
 M src/order.js
R  src/legacy.js -> src/orders-v2.js
MM src/stock.js
A  src/utils.js
?? notes.txt
?? reports/
```

Напоминание про коды: первый символ — индекс, второй — рабочая папка, `??` — новый файл, за которым Git не следит. Имя с пробелом Git берёт в кавычки. У переименования после кода идёт запись «старое -> новое».

## Цель

Допишите функцию `parseStatus(output)` в `index.js`. Она принимает текст вывода `git status --short` (строки разделены переводом строки) и возвращает объект с тремя массивами имён в порядке вывода:

```js
{ staged: [...], unstaged: [...], untracked: [...] }
```

## Критерии приёмки

- `staged` — файлы, у которых первый символ кода не пробел и не `?`. Для переименования указывается новое имя.
- `unstaged` — файлы, у которых второй символ кода не пробел и не `?`.
- Файл с кодом `MM` попадает и в `staged`, и в `unstaged`.
- `untracked` — файлы с кодом `??`; они не попадают в другие списки.
- Кавычки вокруг имени убираются: `price lists/may 2026.csv`.
- Пустые строки и перевод строки в конце текста игнорируются. Пустой вывод даёт три пустых массива.

## Ограничения

- Не используйте регулярные выражения.
- Менять только тело `parseStatus`.
