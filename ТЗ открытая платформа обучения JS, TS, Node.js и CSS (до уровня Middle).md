# ТЗ: открытая платформа обучения JS, TS, Node.js и CSS (до уровня Middle)

Oct 7, 2026 · @beknazar

## 1. Цели, аудитория и принципы

Платформа бесплатно ведёт человека, который знает основы HTML и немного кода, до уровня Middle в JavaScript, TypeScript, Node.js и CSS: каждая тема закрепляется заданиями, похожими на реальные рабочие задачи.

**Аудитория.** Новичок с базой HTML и первым опытом кода (переменные, условия, циклы на любом языке). Тех, кто знает больше, платформа пропускает вперёд через входные тесты модулей. Язык контента: русский; английские термины и названия из документации даются рядом, чтобы человек мог читать оригинал.

**Что значит «Middle» в этом ТЗ.** Выпускник самостоятельно берёт задачу из трекера и доводит её до продакшена: проектирует решение, пишет типизированный код и тесты, читает чужой код и делает ревью, находит причину бага по логам и DevTools, понимает производительность и безопасность, деплоит сервис.

**Принципы**

1. **Открытость.** Все темы и задания доступны сразу, без регистрации, оплаты и «закрытых» уровней. Прогресс хранится в браузере с экспортом и импортом файлом, чтобы не нужны были аккаунты.
2. **Реальность.** Каждое задание оформлено как рабочая ситуация: тикет, баг в чужом коде, вёрстка по макету, интеграция с API, код-ревью. Абстрактные задачи вроде «сложи два числа» допустимы только как мини-разминка внутри урока.
3. **Подробность и простота.** Урок идёт от проблемы к решению: зачем это нужно, как работает, пример, типичные ошибки, задания. Новый термин не используется до того, как объяснён.
4. **Практика важнее чтения.** Ориентир: не меньше 70% времени учащегося уходит на написание и исправление кода (целевой показатель, проверяется на пилоте).
5. **Закрепление синтаксиса руками.** Короткие ежедневные упражнения на набор кода и повторение через интервалы, чтобы синтаксис запоминался до автоматизма.
6. **Обратная связь за секунды.** Любое задание проверяется автотестами прямо в браузере, ошибка объясняется человеческим языком.

## 2. Функциональные требования

Платформа работает как статический сайт: человек открывает ссылку, читает урок, пишет код в редакторе, тесты проверяют решение сразу, а прогресс остаётся в его браузере. **MVP** — первый релиз, **V2** — после пилота.

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-01 | Каталог: модули → уроки → задания. Всё открыто без регистрации, у каждого урока и задания своя постоянная ссылка. | MVP |
| FR-02 | Страница урока: объяснение, схемы, гифки или короткие видео, живые примеры, блок «типичные ошибки», блок «как это выглядит в реальной работе». | MVP |
| FR-03 | Редактор кода в браузере: подсветка, автодополнение, подсветка ошибок TypeScript, горячие клавиши как в VS Code. | MVP |
| FR-04 | Запуск JS и TS и автотесты в изолированной среде (Web Worker). Результат по каждому тесту, ошибки объяснены человеческим языком, а не только стектрейсом. | MVP |
| FR-05 | HTML и CSS задания: живой предпросмотр, проверка DOM и стилей тестами, сравнение со скриншотом макета с допуском. | MVP |
| FR-06 | Node.js задания: запуск серверного кода в браузере. Резервный вариант: скачать шаблон проекта и запустить локально командой `npm test` с теми же тестами. | MVP |
| FR-07 | Подсказки в три уровня (направление, шаг, почти решение). После попыток открывается эталонное решение с разбором и типичными неверными вариантами. | MVP |
| FR-08 | Прогресс без регистрации: хранится в браузере (IndexedDB), экспорт и импорт одним файлом для переноса на другое устройство. | MVP |
| FR-09 | Повторение: карточки и мини-упражнения «наберите по памяти» по пройденным темам с интервальным повторением. | MVP |
| FR-10 | Входной тест модуля: можно пропустить знакомое. Итоговый тест модуля с разбором ошибок. | V2 |
| FR-11 | Проекты портфолио: ТЗ как от заказчика, шаблон репозитория, автотесты приёмки, чек-лист самопроверки. | MVP |
| FR-12 | Режим код-ревью: показан чужой diff, человек пишет замечания, затем сравнивает со списком реальных проблем. | V2 |
| FR-13 | Отладочные задания: дано сломанное приложение, логи и стектрейс; нужно найти причину и исправить. | V2 |
| FR-14 | Поиск по курсу, глоссарий терминов с английскими названиями, переход к уроку, где термин объяснён. | MVP |
| FR-15 | Светлая и тёмная тема, адаптив для телефона (чтение уроков), управление с клавиатуры, достаточный контраст. | MVP |
| FR-16 | Офлайн-режим (PWA) для уже открытых уроков. | V2 |

На телефоне полноценное прохождение заданий с кодом не требуется: достаточно читать уроки и повторять карточки.

## 3. Нефункциональные требования и стек

Сайт не должен иметь бэкенда: всё исполняется в браузере пользователя, поэтому нет аккаунтов, нет серверных расходов и нечего ломать при росте посещаемости.

Уроки и тесты собираются в статический сайт. Запуск кода, проверка и сохранение прогресса идут в браузере: среда запуска зависит от типа задания.

**Нефункциональные требования**

| Область | Требование |
| --- | --- |
| Скорость | Страница урока открывается быстро на среднем ноутбуке и слабом телефоне (целевой показатель: первая отрисовка до 2 с). Редактор и раннер подгружаются лениво, только на страницах с заданиями. |
| Безопасность | Код пользователя исполняется только в изоляции (Web Worker, iframe с `sandbox`), без доступа к данным самой платформы. Время выполнения ограничено, бесконечные циклы прерываются. |
| Приватность | Без аккаунтов и персональных данных. Допустима только анонимная статистика без cookies; отказ от неё не влияет ни на что. |
| Доступность | Соответствие WCAG 2.1 AA: клавиатура, контраст, подписи к картинкам, у анимаций есть пауза. |
| Браузеры | Две последние версии Chrome, Firefox, Safari, Edge. Если функция (например, Node в браузере) не работает, платформа показывает причину и предлагает локальный режим. |
| Открытость | Уроки в Markdown/MDX, задания и тесты в обычных файлах в репозитории: любой может предложить исправление через pull request. |
| Поддержка | Версии Node.js и TypeScript закреплены в каждом модуле. Пересмотр уроков на устаревание раз в 6 месяцев. |

**Предлагаемый стек**

| Компонент | Решение | Почему |
| --- | --- | --- |
| Сайт | React, TypeScript, Vite | Привычный стек, быстрая сборка, статический результат. |
| Контент | MDX в репозитории, у каждого задания папка: описание, заготовка, тесты, эталон | Формат «описание + заготовка + тесты + решения» уже проверен в [упражнениях The Odin Project](https://github.com/yashgarg05/javascript-exercises-TOP). |
| Редактор | Monaco Editor | Тот же движок, что в VS Code; подсветка и ошибки TypeScript из коробки. |
| TS и JS в браузере | Компилятор TypeScript в Web Worker, лёгкий раннер тестов с API в стиле Vitest/Jest | Тесты пишутся так же, как в реальной работе. |
| HTML и CSS | iframe с `sandbox`, DOM-тесты, сравнение скриншотов | Проверка и результата, и кода. |
| Node.js в браузере | WebContainer API от StackBlitz, [позволяет запускать Node.js и npm прямо во вкладке](https://www.npmjs.com/package/@webcontainer/api) | Единственное зрелое решение для полноценного Node без сервера. |
| Резервный Node-режим | Шаблон проекта и `npm test` локально | Если WebContainer недоступен, курс не блокируется. |
| Хранение прогресса | IndexedDB плюс экспорт файла | Никаких аккаунтов. |
| Хостинг | Статический хостинг с возможностью задавать HTTP-заголовки (Cloudflare Pages, Netlify) | Нужны заголовки изоляции для WebContainer. |

**Ограничения WebContainer, которые нужно учесть сразу.** Для работы нужна изоляция источника (`SharedArrayBuffer`), и в production без неё не обойтись; блокировщики cookies могут ломать запуск ([документация пакета](https://www.npmjs.com/package/@webcontainer/api)). API бесплатно доступно для личного и open source использования, а для коммерческого использования в for-profit нужна лицензия ([условия StackBlitz](https://webcontainers.io/enterprise)). Поэтому платформа должна оставаться некоммерческим открытым проектом, а Node-задания обязаны запускаться и без WebContainer, в локальном режиме.

## 4. Программа курса

Курс состоит из основной части (модули 0–11) и части с фреймворками (модули 12–14) и занимает около 75 недель при 10–12 часах в неделю. Срок целевой и уточняется после пилота. Каждый модуль заканчивается проектом, который можно показать работодателю. Темы взяты из карт [roadmap.sh](https://roadmap.sh) по JavaScript, TypeScript, Node.js, CSS и Backend и дополнены тем, что реально встречается в рабочих задачах.

## 5. Формат урока и подача материала

Каждый урок строится по одной схеме и заканчивается заданиями, а не итоговым «повторяй за мной». Причина известна из опыта многих учащихся: уроки по принципу «посмотри и повтори» не развивают [решение проблем, отладку и принятие решений](https://kitemetric.com/blogs/escape-tutorial-hell-build-real-coding-skills), поэтому объяснение занимает меньшую часть времени, а основную часть занимает практика.

**Структура урока (10–15 минут чтения, 30–60 минут практики)**

1. **Зачем это в работе.** Короткая рабочая ситуация: например, «заказчик жалуется, что итоговая сумма в корзине иногда неверная».
2. **Объяснение простыми словами.** Новый термин вводится один раз, английское название в скобках, затем используется без изменений. Одна аналогия из жизни, не больше.
3. **Минимальный живой пример.** Код можно менять и запускать прямо в уроке.
4. **Как это работает внутри.** Схема, гифка или пошаговый визуализатор выполнения (область видимости, стек вызовов, event loop, каскад CSS).
5. **Типичные ошибки.** Реальные сообщения консоли и объяснение, что они значат и как искать причину.
6. **Шпаргалка синтаксиса.** Несколько строк, которые нужно знать наизусть; эти строки попадают в карточки повторения.
7. **Задания.** Разминка, основные, реальная задача (раздел 6).
8. **Итог и мостик.** Что теперь умеет человек и что нужно для следующего урока.

**Правила подачи**

- Один урок — одна идея. Если объяснение не помещается в пять абзацев, урок делится.
- Предложения короткие, без жаргона без объяснения. Каждый абзац отвечает на один вопрос.
- Сначала пример, потом правило, а не наоборот.
- Показывать неправильный вариант и почему он не работает рядом с правильным.
- После трудных тем (замыкания, event loop, generics, специфичность CSS) идёт отдельный урок «разбор типичных ловушек» с заданиями на предсказание результата.

**Медиа (гифки, схемы, видео)**

| Тип | Для чего | Требования |
| --- | --- | --- |
| Короткая анимация (гифка или видео) | Показать процесс: как прокручивается event loop, как flex-элементы меняют положение | До 10 секунд, одна идея, без звука. Предпочтительно видео WebM или MP4 вместо гифки (меньше вес), гифка допустима как запасной вариант. |
| Схема (SVG) | Структура, связи, порядок выполнения | Читается без подписи, текст остаётся текстом (можно выделить и перевести), есть подпись для скринридера. |
| Скриншот DevTools | Показать, куда смотреть при отладке | Свежий для текущей версии Chrome, стрелки на нужных элементах. |
| Пошаговый визуализатор | Выполнение кода по строкам с состоянием переменных | Встроенный, управляется кнопками «шаг вперёд» и «назад». |

У каждой анимации есть пауза, у каждого изображения есть описание, а у каждого материала — источник и лицензия. Нельзя использовать чужие изображения без разрешения, схемы рисуются самостоятельно.

## 6. Типы заданий и принципы их составления

В каждом уроке не меньше шести заданий: три разминки, два основных и одна реальная задача. Разные типы нужны, потому что у синтаксиса, понимания и профессиональных привычек разные способы закрепления. Механизмы запоминания опираются на [повторение по памяти и интервальное повторение](https://algocademy.com/blog/?p=1624), поиск и исправление ошибок в чужом коде и ежедневные короткие упражнения.

| Тип | Что делает человек | Реальный аналог | Проверка |
| --- | --- | --- | --- |
| Набрать по памяти | Пишет короткий фрагмент синтаксиса без подсказок | Свободное владение языком без постоянного поиска | Автотест, повторение по расписанию |
| Предсказать результат | Читает код и вводит, что он выведет, потом запускает | Чтение чужого кода, понимание поведения | Сравнение с реальным запуском |
| Исправить баг | Получает баг-репорт (шаги, ожидаемое и фактическое), находит и чинит ошибку | Тикет в трекере | Тесты, включая случай из репорта |
| Реализовать по тикету | Пишет функцию или модуль по описанию с критериями приёмки | Обычная задача спринта | Открытые и скрытые тесты |
| Рефакторинг | Улучшает структуру кода, не меняя поведения | Уборка технического долга | Прежние тесты проходят, линтер и метрики сложности в норме |
| Вёрстка по макету | Повторяет дизайн, адаптивно | Задача от дизайнера | DOM-тесты, сравнение скриншотов, чек-лист доступности |
| Интеграция с API | Подключается к тестовому API с задержками, ошибками, пагинацией | Подключение внешнего сервиса | Мок-сервер с нестабильными ответами |
| Типизация | Описывает типы для данных или переносит JS-модуль на TS | Миграция проекта на TypeScript | Проверка компилятором и тесты на уровне типов |
| Код-ревью | Читает diff и пишет замечания | Ревью pull request | Сравнение со списком реальных проблем в diff |
| Отладка по логам | Получает логи и стектрейс, находит причину | Инцидент на проде | Ответ плюс исправление проходят тесты |
| Скрипт или CLI на Node | Читает файлы, обрабатывает данные, пишет отчёт | Автоматизация рутины | Проверка вывода и кода возврата |
| REST API по спецификации | Реализует эндпоинты по OpenAPI-описанию | Задача backend-разработчика | HTTP-тесты против его сервера |
| Написать тесты | Покрывает чужой код тестами | Работа с кодом без тестов | В код внесены ошибки; хорошие тесты их ловят |
| Мини-проект и проект | Собирает работающий продукт по ТЗ | Задача на несколько дней | Автотесты приёмки и чек-лист |

**Структура задания.** Каждое задание — это папка с файлами: описание (контекст, цель, критерии приёмки, ограничения), заготовка кода, тесты, три подсказки, эталонное решение с разбором, список типичных неверных решений, сложность от 1 до 5, ориентировочное время и теги тем. Такой набор файлов уже работает в [упражнениях The Odin Project](https://github.com/yashgarg05/javascript-exercises-TOP): описание, пустой файл и тесты, плюс отдельная папка с решениями.

**Принципы составления**

1. **Реальный контекст.** Никаких `foo` и `bar`. Данные и имена из реальных областей: заказы, склад, доставка, бронирование, поддержка клиентов, финансы, расписания.
2. **Критерии приёмки измеримы.** Задание формулируется как тикет: что должно происходить, при каких условиях, что считать ошибкой.
3. **Неполные данные в старших модулях.** Начиная с модуля 3 часть заданий содержит неясности, как в настоящем ТЗ. Человек должен задать уточняющие вопросы, перечислить допущения и только потом писать код. Это типичная рекомендация для тестовых заданий: [задавать вопросы заранее и фиксировать план](https://github.com/hackyourfuture/ta_guidelines).
4. **Тесты проверяют поведение, а не реализацию.** Любое корректное решение проходит. Сообщения об ошибках объясняют, что ожидалось и что получено.
5. **Нарастающая сложность и возврат к пройденному.** Старые темы регулярно появляются в новых заданиях, чтобы синтаксис закреплялся через повторное использование.
6. **Практики больше, чем чтения.** Один из распространённых ориентиров: [около 20% времени на изучение, около 80% на создание](https://www.frontendmentor.io/articles/project-based-learning-vs-tutorials). В нашем курсе нижняя граница практики — 70% времени.
7. **Задание можно пройти без регистрации и без внешних сервисов.** Все данные, моки и макеты входят в состав задания.

**Соотношение типов по этапам**

| Этап | Преобладают | Пример реальной задачи |
| --- | --- | --- |
| Модули 0–2 | Набрать по памяти, предсказать результат, исправить баг, вёрстка по макету | Исправить функцию расчёта скидки, у которой при пустой корзине выводится `NaN` |
| Модули 3–5 | Реализовать по тикету, интеграция с API, типизация, рефакторинг | Подключить каталог к API, где часть запросов падает по таймауту, и показать пользователю понятную ошибку |
| Модули 6–8 | CLI на Node, REST API, написание тестов, отладка по логам | Разобрать выгрузку заказов в CSV с ошибочными строками и вывести отчёт |
| Модули 9–11 | Код-ревью, инциденты, мини-проекты и проекты | Найти причину утечки памяти в сервисе по графику потребления и логам |

## 7. Сквозные проекты портфолио

У курса десять проектов, по одному на модуль или группу модулей. Реальные тестовые задания компаний показывают, какого уровня ждёт работодатель: например, [публичное задание Feathr](https://github.com/Feathr/interview-assignment-react) на TypeScript с API, где требования разделены на уровни Junior и Mid, а отзывы кандидатов описывают [задачи с API, сортировкой и пагинацией](https://www.glassdoor.com.mx/Entrevista/mid-level-software-developer-preguntas-entrevistas-SRCH_KO0,28.htm). Проекты курса строятся по тем же образцам, но с собственными данными и тестами.

| № | Проект | Реальный аналог | Что тренирует | Модуль |
| --- | --- | --- | --- | --- |
| P1 | Калькулятор заказа: корзина, скидки, налоги, округление | Расчёты в интернет-магазине | Функции, массивы, объекты, граничные случаи | 1 |
| P2 | Три страницы по макету: карточка товара, форма заказа, панель управления | Вёрстка по макету дизайнера | Flexbox, Grid, адаптив, доступность | 2 |
| P3 | Каталог товаров с поиском, фильтрами и сортировкой по API | Интерфейс над готовым API | DOM, события, `fetch`, история браузера | 3 |
| P4 | Клиент для нестабильного API: повторы, таймауты, кэш, ограничение параллелизма | Надёжная интеграция | Асинхронность, ошибки, `AbortController` | 4 |
| P5 | Типобезопасный SDK для публичного API и перенос P3 на TypeScript | Миграция JS-проекта на TS | Generics, utility types, `strict` | 5 |
| P6 | CLI: пакетная обработка CSV и выгрузок, отчёт в файл | Автоматизация рутины | Потоки, файлы, аргументы, коды возврата | 6 |
| P7 | REST API учёта заказов или склада с БД, авторизацией и тестами | Backend небольшого сервиса | Express/Fastify, SQL, JWT или сессии, валидация | 7–8 |
| P8 | Производственный контур для P7: CI, Docker, деплой, логи | Выкатка сервиса | CI/CD, конфигурация, мониторинг, безопасность | 9 |
| P9 | Ревью пяти pull request и один вклад в настоящий open source проект | Работа в команде | Ревью, Git-процесс, общение | 10 |
| P10 | Выпускной проект по выбору из четырёх ТЗ: доставка, склад, бронирование, поддержка клиентов | Готовый продукт | Всё вместе | 11 |

Проекты P11–P13 фреймворк-части описаны в разделе 4 и оформляются по тем же правилам, что и проекты ниже.

**Как оформляется проект**

1. **ТЗ как от заказчика.** С предысторией, целями, ограничениями и намеренно недосказанными местами. Человек пишет список вопросов и допущений до начала работы.
2. **Шаблон репозитория.** Структура папок, настроенные линтер, форматтер и скрипты, `README` с разделами, которые нужно заполнить.
3. **Изменение требований посередине.** Во всех проектах начиная с P3 приходит дополнение к ТЗ в середине работы: нужно изменить код, не сломав существующее.
4. **Автоматическая приёмка.** Набор тестов проверяет главные сценарии, а чек-лист ревью покрывает то, что тесты не видят: читаемость, структуру, обработку ошибок.
5. **Самооценка и разбор.** После сдачи открывается эталонная структура решения и список типичных проблем. Человек сравнивает со своим кодом и записывает три улучшения.
6. **Публикация.** Каждый проект выкладывается на GitHub с `README`, так складывается портфолио.

**Работа с чужим кодом.** Начиная с модуля 3 каждый проект стартует не с пустой папки, а с существующего кода с недостатками (дублирование, устаревший стиль, баги). Новички часто [не готовы ориентироваться и отлаживать в большом незнакомом проекте](https://dev.to/ilyatech/intern-struggles-with-unfamiliar-codebase-mentorship-and-debugging-practice-offered-as-solutions-49d4), потому что учебные материалы редко это тренируют.

Задания и объяснения собираются из интернета и опыта людей, но не копируются: каждый материал сначала служит образцом, затем переписывается под свои данные и тесты. Так курс остаётся законным и единым по стилю, а источники дают реальность и проверенные идеи.

**Что берём и откуда**

Что говорят люди, прошедшие этот путь, сходится в нескольких пунктах, и они уже заложены в курс: нужно переходить от просмотра к [самостоятельным проектам](https://dev.to/ikechukwu/how-to-escape-tutorial-hell-4pi2), начинать с небольших проектов, а не с «клона Netflix» ([опыт автора на freeCodeCamp](https://www.freecodecamp.org/news/how-to-break-free-from-tutorial-hell/)), и учиться [читать сообщения об ошибках, пользоваться отладкой и Git, принимать ревью](https://dev.to/zainaboyedeji/common-mistakes-beginner-software-engineers-make-and-how-to-avoid-them-1em6) как часть работы.

**Конвейер создания одного задания**

1. **Образцы.** Найти не менее трёх прообразов: реальный тикет или баг, публичное тестовое задание, задача из открытого проекта.
2. **Переписать.** Сформулировать как тикет со своими данными и именами. Определить критерии приёмки.
3. **Тесты и эталон.** Написать тесты, эталонное решение и три заведомо неверных решения (частичное, с гонкой, с пропущенным краевым случаем).
4. **Проверка тестов.** Эталон проходит все тесты, каждое неверное решение проваливает хотя бы один. Иначе тесты дорабатываются.
5. **Чек-лист качества.** Контекст реальный, критерии измеримы, тесты не привязаны к реализации, сообщения об ошибках понятны, три подсказки написаны, время оценено, нет устаревшего API.
6. **Пилот.** Первые учащиеся проходят задание; кнопка «задание непонятно» показывает, где застряли. Задание с повторяющимися жалобами переписывается.
7. **Публикация и обратная связь.** Версия задания в репозитории, на странице кнопка «задание непонятно», разбор обращений раз в две недели.

**Кто пишет курс.** Все уроки, задания, тесты и разборы пишет Claude, команды авторов нет. Это быстро, но у ИИ бывают ошибки и устаревшие знания, поэтому автоматическая проверка обязательна:

1. Эталонное решение каждого задания и три неверных запускаются в CI на закреплённых версиях Node.js, TypeScript и React. CI бесплатен для открытых репозиториев (например, GitHub Actions).
2. Примеры кода из уроков тоже запускаются автоматически.
3. Факты об API сверяются с официальной документацией (MDN, Node.js, TypeScript, React).
4. На каждой странице есть кнопка «нашёл ошибку», она ведёт в открытый трекер, исправления принимает любой желающий.

Урок, код которого не проходит проверку, не публикуется.

**Лицензия самого курса (предложение).** Тексты уроков под CC BY-SA 4.0, код платформы и тестов под MIT. Так сообщество может исправлять и переводить курс, а заимствования из MDN остаются совместимыми по лицензии.

## 9. Этапы реализации, метрики и риски

Платформу и контент делают параллельно: написание уроков идёт на один модуль впереди разработки функций, которые для этого модуля нужны. Сроки оценочные.

**Этапы**

1. **Фундамент (4–6 недель).** Репозиторий, каркас сайта, движок урока на MDX, редактор, раннер JS и TS в Web Worker, формат задания, прогресс в IndexedDB, карточки повторения. *Критерий перехода:* один урок с пятью типами заданий проходится от начала до конца, тесты показывают понятные ошибки.
2. **Пилотный модуль (6–8 недель).** Модули 0–1 целиком, около 20 уроков и 120 заданий. *Критерий перехода:* первые 10 учащихся из сообщества, не менее 60% дошли до конца, обращения «задание непонятно» разобраны.
3. **CSS и браузер (8 недель).** Модули 2–3, предпросмотр, DOM-тесты, сравнение скриншотов, мок-сервер для API-заданий.
4. **Асинхронность и TypeScript (8 недель).** Модули 4–5, проверка типов в браузере, тесты уровня типов.
5. **Node и backend (10 недель).** Модули 6–8, запуск Node в браузере и локальный режим, HTTP-тесты, задания с БД.
6. **Продакшен и выпуск (8 недель).** Модули 9–11, режим код-ревью, отладочные задания, шаблоны проектов, чек-листы приёмки.
7. **Открытие и поддержка.** Публикация репозитория, правила участия, разбор предложений сообщества, пересмотр содержания раз в 6 месяцев.

Минимальная версия для запуска (MVP): этапы 1–3, то есть основы JavaScript, HTML и CSS и JavaScript в браузере. Этого достаточно, чтобы курс уже был полезен и можно было получить отзывы.

Часть с фреймворками (модули 12–14) выпускается после основной части. Для неё платформе нужны тесты компонентов в браузере (DOM-окружение в изолированной среде) и закреплённые версии библиотек.

**Метрики (целевые, пересматриваются после пилота)**

| Метрика | Цель |
| --- | --- |
| Доля прошедших модуль среди начавших | Не менее 60% |
| Задания, где застревает больше 40% людей | Переписываются в течение месяца |
| Доля заданий, решённых без подсказки третьего уровня | Не менее 70% |
| Время на задание против заявленного | Отклонение не более 50% |
| Выпускной проект сдан с первой или второй попытки среди дошедших до модуля 11 | Не менее 50% |
| Сообщения «задание непонятно» | Разобраны за две недели |

**Риски**

| Риск | Что делаем |
| --- | --- |
| Огромный объём контента (около 75 недель материала), который пишет один автор (ИИ) | Выпускать по модулям, MVP на модулях 0–3, принимать правки от сообщества |
| Node в браузере зависит от технологии StackBlitz, её условий и заголовков изоляции | Локальный режим как полноценная замена; Node-задания проектируются так, чтобы тесты работали в обоих режимах; проект остаётся некоммерческим |
| Лицензии заимствованного материала | Образцы переписываем, прямое заимствование только из источников с совместимой лицензией и с указанием автора; ведётся реестр источников |
| Устаревание содержания (версии Node.js и TypeScript, API браузеров) | Закреплённые версии, пересмотр раз в 6 месяцев, автоматическая проверка, что эталонные решения проходят тесты на актуальных версиях |
| Потеря прогресса из-за очистки браузера (нет аккаунтов) | Экспорт файлом, напоминание о резервной копии после каждого модуля |
| Пассивное чтение вместо практики | Доля практики не ниже 70%, проекты с первых недель, задания стартуют с пустого файла или сломанного кода |
| Исполнение чужого кода в браузере | Изоляция в Worker и iframe, лимиты времени и памяти, никакого доступа к данным платформы |
| Завышенные ожидания «станет Middle за курс» | Честное описание результата на главной странице: знания и портфолио уровня Middle, опыт набирается на практике |

**Принятые решения**

- Язык контента: русский.
- Уроки, задания и тесты пишет Claude; проверка автоматическая и от учащихся (раздел 8).
- Всё бесплатно: курс, хостинг на бесплатном тарифе статического хостинга, бесплатный поддомен вместо купленного домена, бесплатный CI. Платных сервисов в плане нет.
- После модуля 11 добавлены React, Redux Toolkit и MobX (модули 12–14).
- Лицензии по умолчанию: CC BY-SA 4.0 для текстов и MIT для кода; можно изменить.
